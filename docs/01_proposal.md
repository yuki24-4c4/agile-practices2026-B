# 学内施設・備品予約貸出管理システム 初回提案書（第1版）

## 1) システム概要
* **目的**：現在、紙・口頭・表計算ファイルで個別管理されている学内施設および備品の予約・貸出業務を一元化し、Web上で予約・承認・状態管理を行えるシステムを構築する。
* **背景**：台帳と表計算ファイルの不整合による予約重複や確認漏れの発生、空き状況や承認状況の問い合わせに伴う待ち時間を解消する。
* **開発環境**：PHP, MySQL/MariaDB (XAMPP), HTML, CSS, JavaScript, Git, GitHub, VSCode
* **開発規模・期間**：前半セット第1回〜第7回（授業内での動作確認を目的とした学内向けシステム）

---

## 2) 利用者と解決する課題
* **最も重要な利用者**：**一般学生**
  * **選定理由**：要望書第2章「実現したい状態」において、「学生が自分で施設・備品を探し、予約申請と状況確認ができるようにする」ことがプロジェクトの出発点であり、最も高頻度で本システムに関わる利用者であるため。
* **最優先で解決すべき課題**：**「紙と表計算ファイルの不一致による予約重複や確認漏れ」（第1.2章 困りごと2）**
  * **選定理由**：待ち時間や集計の手間といった他の課題は申請を早める等の運用でカバーできるのに対し、予約重複や確認漏れは「制度自体の利用破綻」に直結する致命的なリスクであるため。
* **その他の利用者**：
  * **管理担当者（学務課職員・担当教員）**：申請の承認・却下、貸出・返却のステータス管理を行う。
  * **教員**：学生同様の予約利用者か、管理補助者か権限は未確定。

## 4) 第7回までのMVP候補
前半セット第7回までに完成させる最小実用製品（MVP）は、「予約重複を起こさず、申請から承認・返却までを一元追跡できるコアフロー」に絞り込みます。

1. **認証・権限管理**：学生と管理担当者の識別・分離ログイン
2. **予約申請機能**：対象備品・利用日を指定した申請登録
3. **重複チェックロジック**：同一期間の重複予約をデータベース・システム側で防止
4. **管理者の承認・ステータス管理**：申請の承認/却下、貸出中/返却済みの切り替え
5. **学生の状況確認**：自身が申請した予約のステータス閲覧

## 6) 未確定事項・依頼者への質問（要望書第11章より優先順位付け）

* **【最優先（仕様決定に直結）】**
  1. **重複予約の防止レベル**：同日・同時間帯に重複申請があった場合、エラーとして登録自体を弾く仕様でよいか？
  2. **予約単位**：利用時間の単位は「日単位」固定で問題ないか（時間単位の分割は不要か）？
  3. **承認運用**：すべての予約を管理者の手動承認とするか（自動承認とするケースはあるか）？
* **【中優先（運用ルール）】**
  4. **キャンセル**：学生自身による申請取り消しは「承認前のみ可能」とするか、あるいは貸出直前まで可能とするか？
  5. **教員の権限**：教員専用の独立権限を設けるか、当面は「管理担当者」または「一般学生」のどちらか一方として扱うか？
  6. **削除とデータ保全**：誤削除防止のため、物理削除ではなく「利用停止（論理削除）」フラグによる非表示化で合意できるか？
* **【低優先（第7回以降の検討）】**
  7. **延滞管理・集計**：返却予定日超過時の強調表示（アラート）や集計機能の具体的な算出ルール。

## 7) チーム独自の追加提案（1件）
* **提案内容**：**「予約状況・空き日程のシンプルカレンダー（タイムライン）表示」**
  * **背景と狙い**：WISH-03（一覧）やWISH-04（検索）の優先度を下げた場合でも、予約申請時に「どの日程がすでに埋まっているか」が視覚的に分かれば、学生が無駄な重複申請を行わずに済み、管理者の却下対応の手間も大幅に削減できるため。
  * **制約適合性**：第8章の「外部カレンダー連携（Googleカレンダー等）」は対象外ですが、本システム内（DB上の予約データ）で描画する簡易的な月間/週間テーブル表示であれば、外部連携制約に反せず実装可能です。

## 9) 現時点の仮説・前提条件

* **仮説1（予約単位）**：第7回までの実装では、時間の細かなコマ管理は行わず、「日単位（利用開始日・返却予定日）」でスケジュールを管理する。
* **仮説2（教員権限）**：教員専用の第三の権限は設けず、管理業務を行う教員は「管理担当者」、予約のみを行う教員は「一般学生」アカウントとして運用する（第7回の工数削減のため）。
* **仮説3（データ削除）**：台帳データや予約履歴は物理削除（DELETE）せず、状態フラグ（利用停止・キャンセル）で管理することで誤削除を防ぎ、履歴を保全する。
* **前提条件1（テストデータ）**：実在の個人情報は用いず、架空の学籍番号・教職員番号・備品名データを用いて検証を行う。
* **前提条件2（実行環境）**：PCブラウザ（ChromeまたはEdge）での動作を保証し、スマートフォン等への完全なレスポンシブ対応は前提としない。
